# Evidência: JWT RS256 ponta a ponta no EKS (02/11/2026)

Cluster `ganjj` no Learner Lab, 23 pods `1/1 Running`, chamadas pelo hostname do ELB (gateway como entrada única). Login com o ADMIN do Secret `authorization-credentials` do próprio cluster. Registrados só status HTTP e claims; nenhuma senha nem token.

## PROMO-002 (promotion#49): `GET /api/campaigns`

| Caso | Esperado | Obtido |
|---|---|---|
| `GET /auth/public-key` (PEM público) | 200 | 200 |
| `POST /auth/login` admin (`iss=ganjj-authorization`, `typ=access`, `role=ADMIN`, `sub` e `email` presentes) | 200 | 200 |
| Rota admin com access token | 200 | 200 |
| Sem token | 401 | 401 |
| Refresh token como bearer | 401 | 401 |
| Token expirado | 401 | 401 |
| `iss` errado | 401 | 401 |
| `typ=refresh` | 401 | 401 |
| Assinatura adulterada | 401 | 401 |
| Formato inválido | 401 | 401 |

Os tokens expirado, com `iss` errado e com `typ=refresh` foram assinados com a `private.pem` local, cujo hash bate com o do Secret `jwt-keys` do cluster.

Não executados aqui: `role=CLIENTE` com 403 (sem conta de cliente criada) e `JWT_PUBLIC_KEY` vazia com 500 (exigiria derrubar a configuração). Ambos foram rodados em 21/10 (ver `integration-issues.md`).

## Achado: chave pública do promotion divergente

Na primeira rodada, a rota admin deu 401 com `Assinatura do token inválida`. O `promotion-config` no cluster trazia o `JWT_PUBLIC_KEY` de exemplo versionado em `k8s/configmap.yaml`, diferente da chave do `authorization`; gateway e order usam o ConfigMap `jwt-public-key`, que bate. Correção neste cluster: `JWT_PUBLIC_KEY` do `promotion-config` trocado pelo conteúdo de `jwt-public-key` e restart de `promotion` e `promotion-consumer`; depois a rota admin respondeu 200. O `eks/apply.sh` do api-gateway não faz essa troca, então um cluster novo repete o erro até ele ser ajustado.
