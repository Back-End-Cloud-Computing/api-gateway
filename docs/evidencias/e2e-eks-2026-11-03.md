# Evidência: ensaio no EKS com cupom (03/11/2026)

Cluster `ganjj` criado em 03/11 (2 nodes `t3.large`, `eksctl`, sem precisar do `vpc-cni`), 23 pods `1/1 Running`, chamadas pelo hostname do ELB, gateway como entrada única. Comprador: conta CLIENTE criada no próprio cluster; produto criado pelo ADMIN do Secret `authorization-credentials`. Só status HTTP, ids e totais; nenhuma senha nem token. O cluster foi apagado no mesmo dia, sem NAT, ELB, EC2 ou volume sobrando.

## Fluxo com cupom pelo gateway

| Etapa | Resultado |
|---|---|
| `db:seed --force` do promotion | cupom `BEMVINDO10` com `usage_count` 0 |
| `POST /auth/register` e `POST /auth/login` (CLIENTE) | 201 e 200 |
| `POST /products` (preço 100, estoque 10) | 201 |
| `POST /api/cart/items` (2 unidades) | 201 |
| `PUT /api/cart/coupon` com `BEMVINDO10` | 200, subtotal 200, total 180, `coupon.applied=true` |
| `POST /api/pedidos` com `Idempotency-Key` | 201, `Pending`, **total 180** (em 02/11, sem cupom, era 200) |
| Mesma `Idempotency-Key` de novo | 201, mesmo id de pedido |
| Estoque do produto depois | 8 (um único decremento) |
| Consumer do promotion | `OrderConfirmed processado` com `outcome=consumed` |
| `usage_count` do cupom | 0 → 1 |
| Filas e DLQs | `promotion.order-confirmed` e `support.order-created` com 1 consumidor e 0 mensagens; DLQs em 0 |

É a primeira prova no EKS de que o cupom vai do Cart ao Order, ao evento `OrderConfirmed` e ao consumer (shopping-cart#13, order#25).

## JWT

| Caso | Esperado | Obtido |
|---|---|---|
| CLIENTE em rota admin (`GET /api/campaigns`) | 403 | 403 |
| ADMIN na mesma rota | 200 | 200 |
| Sem token | 401 | 401 |
| `JWT_PUBLIC_KEY` do promotion vazia, ADMIN em `/api/campaigns` | 500 | 500 |
| Chave restaurada (patch do ConfigMap e novo rollout) | 200 | 200 |

CLIENTE→403 e a chave vazia→500 nunca tinham sido rodados no EKS (a nota de 02/11 os listava como não executados).

## Balanceamento e resiliência

| Verificação | Resultado |
|---|---|
| 10 requisições a `GET /api/sale`, gateway (`x-gateway-served-by`) | 5 e 5 entre os 2 pods |
| Mesmas 10 requisições, promotion (`x-served-by`) | 7 e 3 entre os 2 pods |
| `kubectl delete pod` num pod do gateway, 5 requisições seguidas | 5 respostas 200; o Deployment recriou o pod |

## Achados

- O `POST /api/pedidos` exige `rua` no endereço, mas o OpenAPI do Order diz `logradouro` (order#27).
- Um segundo `db:seed --force` devolveu exit 1; o primeiro tinha aplicado. Não investigado.
- Ao restaurar o ConfigMap com `kubectl apply` do YAML exportado, deu conflito de versão; o `patch` resolveu.

## Não testado

- Imagem do embedding-reranking com o modelo embutido (o pod subiu `Running`, sem chamada de embedding).
- LLM real e criação de produto com descrição gerada por IA: `POST /products` foi feito com `generate_description_with_ai=false`; o `llm-provider` e a chave do OpenRouter não foram exercitados no cluster.
